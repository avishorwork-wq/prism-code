Open SLOW 0.1.7 · FAST 0.2.3 · FAST camera · Current simulator

Geometry residuals, derivatives, normal-equation sums and blur are now scalar double-precision C compiled to a small WebAssembly module embedded in the offline page. The algorithm and payload checks are unchanged. No network fetch, library or paid service is needed at runtime. If WebAssembly is unavailable, JavaScript does the same work.

FAST 0.2.3: give clean reads time to finish.

Open FAST 0.2.3 · FAST camera · SLOW 0.1.6 · Current simulator

The first FAST stage previously stopped after 150-225 ms, even when a clean read needed only a little more time. It now gets up to 700 ms within the same overall 950 ms acceptance budget. This avoids abandoning a valid clean image early and then spending the remaining time normalizing it. An exact max-filter rewrite also cuts temporary object allocations. Same cells, RS, payload CRC and strict text checks. FAST and SLOW remain separate.

Measured, not a phone guarantee

In a paired browser test with 4x CPU slowdown, using all six sizes, both palettes and four ECC levels at full capacity, the current version read 48/48 exactly; 0.2.2 read 19/48 in that run. The order was alternated. CPU slowdown is only a simulation, not an actual phone. Browser warmup and scheduling affect near-deadline outcomes; these counts are this test set, not a general accuracy estimate.

A separate candidate run read all 48 exactly, with the slowest read at 634 ms. Timings include decoding but exclude image rendering and pixel readback. No successful result is accepted after the overall acceptance deadline, but a failed computation can still run longer than one second before it notices the deadline.

Checks against losing earlier successes

Desktop: 48/48 full-capacity clean checks retained. Across 96 paired ordinary and harder simulated photos, 56 exact reads in each version and no earlier success lost. This includes tilted/lighted, cylindrical/tinted and glare scenes. These remain synthetic images, not real print/phone captures. White, black, random RGB and corrupted-data checks reject; two fresh payloads in the same decoder both match exactly and a following blank image does not reuse the old result.

Blind resizing was tested but is not enabled: it helped some images and lost others, especially dense grids. There is no claim that every image gets faster or that every damaged image will decode.

SLOW work continues

SLOW stays at 0.1.6. Its supplied 4,000-byte glare JPEG remains about 1.5-1.8 seconds on this desktop, and about 6.15 seconds in the earlier 4x CPU simulation. A new exact blur-kernel experiment speeds the isolated filter but has not shown a consistent whole-image gain, so it is not being shipped as an improvement. The next target is the actual geometry work and difficult fallback cases.

Scanning speed, with the checks kept.

SLOW 0.1.6 and FAST 0.2.2. Same original hex cells and corner notch. Same RS format. Separate readers, no automatic chaining.

Open SLOW 0.1.6 · Open FAST 0.2.2 · FAST camera · Current simulator

The supplied 4,000-byte glare photo

SLOW fell from 43.4 seconds to about 1.7 seconds in the same desktop-browser environment. The exact decoded bytes, CRC-32 and SHA-256 match the earlier verified result. New analytic geometry fitting and a short ranked search avoid repeating the expensive search. Original recovery fallbacks remain when the new path does not pass validation.

A 4x CPU-slowdown simulation took 6.15 seconds. This is not a physical-phone test. A one-second result on your phone is not demonstrated.

FAST and ordinary captures

An exact spatial index replaces repeated full-reference searches. Across paired clean size-5 tests, desktop worker times fell from roughly 330-350 ms to 150-165 ms. Both versions pass all 48 clean size/palette/ECC combinations.

A low-resolution large-code gate now lets smaller large-grid cells reach decoding before deciding they are too small. Full ECC and payload CRC are still required. In 24 paired ordinary simulated captures, successes increased from 18 to 20, with no earlier success lost. This is a small synthetic test, not a camera-accuracy guarantee.

The simulator's clean 4,000-byte image read in about 235 ms with FAST and 239 ms with SLOW in this desktop run. Large high-resolution input under a separate 4x CPU-slowdown test still misses FAST's deadline. Processing budgets are best-effort and some failed attempts can exceed one second.

Slower cases and limits

One retained difficult cylinder went from 11.4 seconds to about 1.5 seconds; another was about 1.4 seconds slower because the quick attempt failed before an old fallback recovered it. The new path is not a universal speedup. Severe damage, some random/no-code images and hard geometry may still require a long search or fail.

SLOW passes 48/48 full-capacity clean checks. The quick color path separately passes four fresh ECC levels and whitening/payload-swap checks, and rejects corrupted data, blank images and random RGB noise. The standalone page was checked with the glare photo, a different supplied photo, stop/cancel, and 390px layout. Only validated payloads are displayed; no universal guarantee against undetected errors is claimed.

Work continuing

Priority: large-code phone-class speed, stronger ordinary-photo recovery, and hard cases that still fall through to repeated searches. Next results will use matched images and include slower cases.
